# 多相机 · 资源页（V2，已实现）与资源评估

> 状态：已实现（YoloFool「多相机 · 资源」标签页，最后一个 Tab）
> 目标：同时打开多组相机，一屏预览，实时记录每路 CPU / 内存 / 帧率，并给出可扩展路数的评估

## 1. 页面能力

- 左侧相机列表：每行一台相机（相机索引 0..N-1，可手动增删），列出 状态 / 分辨率（请求值与实际值不一致时显示 `实际←请求`）/ fps / CPU 均%。
- 预览墙：每路一个缩略图（默认 480×270），叠加 状态、分辨率、fps、像素格式、CPU 均/峰值、帧缓冲。
- 采集设置面板（对选中相机生效，`应用并重开` 后重新打开设备）：
  分辨率（640×480 / 800×600 / 1280×720 / 1920×1080 / 自定义 W×H）、帧率、像素格式（自动 / MJPG / YUY2）、
  曝光（自动/手动 + EV）、白平衡（自动/手动 + 色温）、增益、亮度、对比度、饱和度。
  面板底部「实际：W×H 格式 @fps api」显示驱动真正给到的参数。
- 右侧「本进程资源」：整进程 CPU、工作集 / 私有内存、句柄数、线程数、进程运行时长。
- 仅实时显示，不落盘（无 CSV、无录像）。关闭页签或关窗时全部释放。

## 2. 实测数据（本机 i9-10900 / 32GB / Win10 19045，USB 摄像头，YUY2）

### 整进程口径（程序本身，模型已加载、未开相机）

| 指标 | 实测 |
|---|---|
| 整进程 CPU | ≈0.0 %（单核） |
| 工作集 / 私有 | 279 MB / 230 MB |
| 线程 / 句柄 | 44 / 558 |

开相机后每路追加：720p ≈3 % 单核 + ≈45 MB；1080p ≈4 % 单核 + ≈85 MB。
即 2 路 720p 的整个程序大约是 **7 % 单核（0.35 % 整机）+ 370 MB**。

### 单路分解（采集线程口径，只含缩放+拷贝）

单路，采集线程只做 `Read` + `Cv2.Resize`(INTER_LINEAR→480×270) + 一次 Marshal 拷贝，不画 UI：

| 分辨率 | 实测 fps | 取帧间隔 | 采集线程 CPU 均 | 整进程 CPU/路 | 每路新增内存 |
|---|---|---|---|---|---|
| 640×480 | 29.1 | 34 ms | 1.0–1.5 % | ≈2–3.5 % | ≈23–34 MB |
| 1280×720 | 9.8 | 102 ms | 0.5–1.0 % | ≈3 % | ≈41–52 MB |
| 1920×1080 | 4.9 | 204 ms | 0.8–1.7 % | ≈3–4 % | ≈76–87 MB |

两路同时打开（各自独立 STA 线程）：720p 两路 9.8 / 9.2 fps，整进程 6 %（单核占比）、工作集 105 MB；
1080p 两路 4.9 / 5.1 fps，整进程 6 %、工作集 175 MB。

UI 绘制成本（此前实测，按每帧每次）：

| 操作 | CPU |
|---|---|
| 采集线程 Resize(INTER_LINEAR) + 拷贝到 480×270 | 0.16–0.23 ms |
| UI 线程 Bitmap 拷贝 + 1:1 贴图 + 叠加文字（480×270） | 0.47 ms |
| UI 线程同上（320×180 / 640×360） | 0.23 ms / 0.70 ms |

即 8 路 @15fps：采集线程合计 2–3 %，UI 合计 3–8 %（都按单核算）。`INTER_AREA` 在这版 OpenCvSharp 上异常慢（12–25 倍），已统一用 `INTER_LINEAR`。

## 3. 为什么帧率上不去（关键结论）

- 驱动回读的 FourCC 永远是 **YUY2**（未压缩），请求 MJPG 不生效 ⇒ USB2 的 480 Mbps 实际吞吐 18–20 MB/s 决定了上限：
  640×480≈29 fps、1280×720≈10 fps、1920×1080≈5 fps，正好等于 `带宽 / (宽×高×2)`。
- 两路 720p 能同时跑到约 10 fps，是因为两块相机挂在**不同的 USB 集线器实例**上（`&0&C90F727` / `&0&1EE71B86`），没有互相抢同一条总线。
- 结论：**CPU 与内存从来不是瓶颈，USB 带宽和同一控制器下的相机数量才是。**

## 4. 扩展路数评估（本机）

以 720p 为例的线性外推（单路 ≈3 % 单核 + ≈45 MB，UI ≈0.5 %/路 @10fps）：

| 路数 | CPU（20 线程整机占比） | 内存 | 可行性 |
|---|---|---|---|
| 2 路 | ≈0.35 % | ≈0.1 GB | 已验证，轻松 |
| 4 路 | ≈0.7 % | ≈0.2 GB | CPU/内存无压力，需要 2 个以上 USB 控制器 |
| 8 路 | ≈1.4 % | ≈0.4 GB | 同上，须分散到 4 个控制器，或换 USB3 相机 |
| 16 路 | ≈3 % | ≈0.8 GB | CPU 仍够，带宽需 ≈300 MB/s ⇒ 必须 USB3 相机/控制器或 MJPG 压缩 |

1080p 约为 720p 的 2 倍资源：8 路 1080p ≈ 0.6–0.7 GB 内存、≈1 % 整机 CPU，但带宽需求 8×124 MB/s 在 USB2 上不可能，只能 USB3。

工程建议：

1. 本机（现有 USB2 相机）**4 路以内**可放心用；超过 4 路先解决 USB 控制器数量（每控制器 ≤2 路 720p）。
2. 要 8 路以上：换 USB3 相机（或支持 MJPG 的相机，带宽降到 1/5–1/8），CPU 余量非常大。
3. 内存按 ≈45 MB/路（720p）、≈85 MB/路（1080p）预留；每路另有自己的一份帧缓冲，已在页面上显示。
4. 预览墙超过 8 路时，把 UI 刷新帧率降到 10 fps 以内（目前 30 Hz 定时器取最新帧），否则 UI 贴图会成为主要开销。

## 5. 已知限制

- 相机按 OpenCV 索引枚举；索引不存在时打开会在 10–25 s 后失败并占满一个核，UI 不卡（每路独立 STA 线程），页面显示失败原因。
- 曝光/白平衡等属性是否生效取决于相机驱动；页面「实际：」一行给出驱动回读值。
- 「本进程资源」是整个进程（含 YOLO 推理）的占用，不是单路相机的。
