# 多相机资源监控页方案

> 状态：方案（未实现，等待确认后再动手）
> 目标：在 YoloFool 里加一页，同时打开多组相机，实时记录每一路的 CPU / 内存占用，并给出本机容量评估。
> 独立性：该页不改动识别、针床、学习训练页的任何逻辑；只复用 `Theme`、`AppPaths`、`Log` 和 OpenCV 采集能力。

## 1. 为什么单独做一页

现在程序里所有相机都是"打开一路、采一张、关掉"的用法（`Core/Fixture/FixtureCamera.cs`），
没有任何常开、多路、看资源的入口。要做容量评估，需要一个能**同时持有 N 路常开流**并且
**把指标按路记录成表**的页面，而不是靠任务管理器目测。

## 2. 页面长什么样

Tab 文本：`多相机 · 资源`，挂在 `针床检测` 之后（`MainForm.cs` 的 `BuildTabs()`）。

```
┌───────────────────────────────────────────────────────────────────────────┐
│ [＋摄像头] [＋视频文件] [▶ 全部开始] [■ 全部停止] [导出 CSV]   采样 1s  ●就绪 │
├──────────────────────────────────┬────────────────────────────────────────┤
│ 相机表（DataGridView，可多选）    │ 预览 2×2（可选，默认关，≤10fps/≤480px） │
│ # │名称│源│组│状态│分辨率│fps│取帧ms│ ├────────────────────────────────────────┤
│   │    │  │ │运行│1280×720│9.8│0.06 │ │ 本进程                                │
│   │    │  │ │运行│视频X.avi│30 │6.4  │ │ CPU 18%  内存 612MB  私有 480MB        │
│   │    │  │ │错误│-       │-  │-    │ │ 线程 26  句柄 512  GC堆 8MB            │
├──────────────────────────────────┴────────────────────────────────────────┤
│ CSV: captures\multicam\multicam-20261119-164500.csv   记录中 · 已写 12800 行  │
└───────────────────────────────────────────────────────────────────────────┘
```

要点：
- **表是主角，预览是配角**。预览自身要吃 GDI+ 和 UI 线程时间，开着看指标就一定不准，
  所以默认关闭，勾选后才画，并且强制节流到 10fps、缩到 ≤480px 宽。
- 相机表 11 列，用 `Theme.StyleGrid` 统一样式；组级汇总用一行灰色 `组合计` 插入组尾。
- 指标刷新每 500ms 一次（`BeginInvoke` 合并，多个采样只刷一帧），采集线程绝不碰控件。

## 3. 相机源

| 源 | 说明 | 用途 |
| --- | --- | --- |
| 摄像头 | OpenCV `VideoCapture(index, DSHOW/MSMF/ANY)`，沿用 `FixtureCamera` 的回退顺序 | 真实占用 |
| 视频文件 | `VideoCapture(path)` 循环播放（到尾 seek 0） | 没有 N 台相机时压测，也用于对比解码成本 |

分组是**逻辑标签**（`GroupName`），不影响打开顺序；支持按组一键启停，表里插组合计行。

## 4. 指标定义与采集原理

### 4.1 每路（在各自的采集线程内自测，避免跨线程 OpenThread）

| 指标 | 取法 |
| --- | --- |
| fps | 帧计数 / 墙钟 |
| 取帧耗时 ms | `Stopwatch` 包 `cap.Read()` + `Clone()`。**注意它是"等到下一帧"的时间，不是 CPU 开销** |
| 线程 CPU % | `GetThreadTimes(GetCurrentThread())` 增量 / 墙钟（这个才是真 CPU） |
| 分配速率 MB/s | `GC.GetAllocatedBytesForCurrentThread()` 增量（查托管泄漏） |
| 帧缓冲 MB | `Mat.Total × ElemSize()`（每路必有的一份） |

### 4.2 整进程（同一个 `Process` 实例，每采样 `Refresh()`）

`TotalProcessorTime` 增量 / 墙钟 / `ProcessorCount` = CPU%；
`WorkingSet64`、`PrivateMemorySize64`、`Threads.Count`、`HandleCount`、`GC.GetTotalMemory(false)`。

### 4.3 内存归因的诚实说明

同进程内 GC 堆、非托管帧缓冲、DirectShow 内部缓冲是共享的，**没有可靠的 API 能把字节数切给某一路**。
所以页面给三档：
1. **帧缓冲 MB**：每路确定的一份（1080p = 5.93MB，720p = 2.64MB）；
2. **分配速率**：该线程自己的托管分配，涨而不落就是它漏了；
3. **整进程增量**：拿"打开前基线"和"当前值"对比，N 路一起涨时可以按路平摊做估算，表里标注"估算"。
真要做到每路精确，只能每路开子进程 —— 复杂度高、进程间传帧代价大，**本方案不做**。

### 4.4 CSV

`captures\multicam\multicam-yyyyMMdd-HHmmss.csv`，每次采样写 N 行（每路一行，含整进程列）。
列：`时间,索引,名称,源,组,状态,分辨率,fps,取帧ms,线程CPU%,分配MB/s,帧缓冲MB,进程CPU%,WS_MB,Private_MB,线程数,句柄数,GC堆MB`。
1s 间隔、8 路、1 小时 ≈ 28800 行 ≈ 3MB，够用；`StreamWriter` 带 `AutoFlush=false` + 每 60 秒 flush。

## 5. 本机实测数据（评估依据）

硬件：Intel i9-10900（10 核 20 线程，2.8GHz）+ 32GB + Windows 10 19045。
测量工具：`tmp/mcprobe`（临时探针，不进仓库），只测采集/解码，不挂预览、不录像。

### 5.1 采集（实机 USB 相机 #0，只读不写）

| 分辨率 | 实测 fps | 单帧 CPU | 带宽推算 | 满载折算每路 CPU |
| --- | --- | --- | --- | --- |
| 640×480 | 29.2 | 0.05 ms | 17.9 MB/s | 约 0.15%（0.03 核） |
| 1280×720 | 9.8 | 0.7–1.2 ms | 18.1 MB/s | 约 1%（0.2 核@30fps） |
| 1920×1080 | 4.9 | 2.1–2.7 ms | 20.3 MB/s | 约 1.3%（0.26 核@30fps） |

关键发现：**三档的 "fps × 像素 × 2 字节" 几乎都是 18–20 MB/s**，且 `FourCC=MJPG` 请求被相机忽略
（帧率不涨）。这说明这台相机是 **USB2 上跑未压缩 YUY2**，瓶颈在总线不在 CPU。
"打开 1080p 只有 4.9fps" 不是算力问题，是带宽问题——这条结论直接决定多路方案的可行性。

### 5.2 解码（MJPEG 视频文件，模拟 30fps 的 MJPG 相机）

| 分辨率 | 单帧 CPU | 单核吞吐 | 30fps 折算每路 |
| --- | --- | --- | --- |
| 1280×720 | 6.4–6.5 ms | 155 fps/核 | **0.19 核（19%）** |
| 1920×1080 | 13.1–13.7 ms | 72 fps/核 | **0.40 核（40%）** |

进程 CPU 随路数线性增长：4 路 397–427%，8 路 823–842%（每路满 100% 计）。

### 5.3 内存

1080p 一路：打开前 WS 23MB / 私有 8MB → 打开并跑 2 秒 WS 99MB（**+77MB**）、私有 82MB（+75MB）；
继续读 10 秒无增长（不随时间泄漏）；关闭后 WS 42MB（**残留 +19MB**）、私有 18MB（+11MB）。

### 5.4 容量评估结论

按"每路 1 采集线程 + 独立帧缓冲"的架构推算（20 逻辑核）：

| 路数 | 场景 | 采集 CPU | 预览（10fps/480p，估算） | 合计占整机 | 内存增量 |
| --- | --- | --- | --- | --- | --- |
| 4 | 1080p30 MJPEG | 1.6 核 | 0.2–0.4 核 | **约 10%** | 约 0.3 GB |
| 8 | 1080p30 MJPEG | 3.2 核 | 0.5–0.8 核 | **约 20%** | 约 0.6 GB |
| 8 | 720p30 MJPEG | 1.5 核 | 0.4–0.6 核 | **约 10%** | 约 0.4 GB |
| 8 | 本机 USB2 相机（1080p YUY2） | 约 0.3 核 | — | 忽略 | 约 0.6 GB |

一句话：**CPU 和内存都不是瓶颈，真正的瓶颈是 USB 带宽。**
- 这台机器上的相机走 USB2 未压缩，1080p 单路就只剩 5fps，8 路会互相抢同一条 480Mbps 总线；
- 多路 1080p30 必须换成 **支持 MJPEG/H.264 输出、接 USB3 控制器**的相机；
- 同一条 USB2 总线上，MJPG 1080p30（约 6–8MB/s）最多 3–4 路；USB3 建议 ≤8 路/控制器。
- CPU 留了 80% 余量，正好够后面挂 YOLO 推理（yolov8n 约 45–50ms/张，1 路 1080p 30fps + 检测抽帧 5fps 时才是真吃 CPU 的地方）。

## 6. 已知坑与对策（都已实测踩过）

| 坑 | 实测现象 | 对策 |
| --- | --- | --- |
| 打开不存在的 index | OpenCV 后台线程里 `Open` 直接失败；主线程里**卡 10–25 秒、烧满约 1.7 核**才返回失败，DSHOW 报 `can't be used to capture by index`，MSMF 报 `-1072875772` | 打开放到 UI 线程发起 + 后台等待，状态显示"打开中…"；超时 8s 标记失败并让用户放弃；**失败不自动重试**，避免反复烧 CPU |
| 后台线程打开相机失败 | `Open` 在非 UI 线程调用会失败（同一 psar 报错） | 所有 `VideoCapture` 构造都走 UI 线程（或 UI 持有的打开线程） |
| 本机第二台相机 index 不可达 | 系统里有 2 个 "Web Camera"，但只有 index 0 能打开 | 页面上给出 index 探测结果和"这个 index 打不开"的明确提示，不假装成功 |
| 预览拖垮 UI | — | 默认关预览；开启后 ≤10fps、缩放 ≤480px、`BeginInvoke` 合并 |
| Mat 句柄泄漏 | 长时间跑无增长已确认，但历史代码有过 | `using`/`Dispose` 严格配对，关闭时 `Join(2000)` 再释放 |
| 内存残留 | 关闭后仍有 +19MB WS | 属 DirectShow 正常回收延迟，页面上"关闭后指标"保留观察；不做强制 `GC.Collect` |

## 8. 实施顺序与验收

1. `CameraStream` + 指标（先不接 UI，用临时 harness 验证数字和探针一致）；
2. 页面骨架：表格 + 添加/启停；
3. CSV + 整进程指标 + 组合计；
4. 预览节流（可选功能最后做）；
5. 关窗/切页清理。

验收标准：
- 1 路实机 + 2 路视频文件同时跑 5 分钟，无崩溃、无卡顿（点击响应 <200ms）；
- 表里 fps 与 `tmp/mcprobe` 实测偏差 <5%；
- 每 30 秒内存采样不单调增长（±5MB 内波动）；
- CSV 行数 = 采样次数 × 路数，字段完整；
- 全部停止后线程数回落、句柄数回落。
